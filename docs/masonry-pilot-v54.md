## 확인한 문제와 수정

1. **원문 첫 줄 누락**: 제목 필드에 들어간 첫 문장을 전체 포괄 분석에서 빠뜨릴 수 있었다. 제목과 본문을 중복 없이 합친 원문 전체를 사용한다. 기존 40개 본문 중 20개가 이 구조에 해당했다.
2. **재료·공법 문맥 누락**: `제품은 견본품을 제출...` 같은 문장은 상위 제목 `내화벽돌`을 함께 해석한다. 서로 다른 벽돌/블록의 전용 조항을 검색에서 걸러내고, 일반 조항과 복합 범위는 유지한다.
3. **GPT 입력 간 문맥 혼동**: 서로 다른 원문 조항을 한 검증 요청에 섞지 않는다. 같은 재료라도 줄눈 치수와 제품 품질처럼 행위가 다르면 대응 근거로 삼지 않도록 검증을 강화했다.
4. **인용 실패**: 화면용 필드 표지만 붙은 실제 인용은 인정하되, 생략·요약·상위 제목만의 인용은 검증 완료로 인정하지 않는다. 실패 사유를 후보에 남긴다.
5. **재료가 다른데 전체 대응 판정**: 실제 GPT가 내화몰탈과 단열 모르타르의 작업 문구가 같다는 이유로 전체 대응을 반환했다. 명시된 재료 명칭이 다르면 시스템에서 `추가 확인 필요`로 낮추고 자동 전체 포괄 근거로 쓰지 않는다. 이것은 재료의 기술적 동등성 여부를 확정하는 판정이 아니다.
6. **결과 표시**: 검색 후보의 의미 대응과 문장 전체 포괄을 분리해 표시한다. 원문별 세부 근거·분석 모델·시각을 열람할 수 있다. 조항 이동은 저장된 분석만 조회하며 유료 GPT 호출을 자동 실행하지 않는다.
7. **중단 복구/개발 안정성**: 시험용 API 응답을 중간 캐시하여 동일 입력을 재호출하지 않고 재현할 수 있게 했다. Word 변환 임시 파일 잠금으로 개발 서버가 종료되는 문제는 임시 디렉터리를 감시 대상에서 제외해 수정했다. 로컬 시험 화면의 `/relay`는 명시적으로 격리 API에만 연결한다.
8. **원문 구간 중복 응답**: 전체 포괄 분석은 고정된 원문 ID를 필수 JSON 키로 받는다. 전체 상태는 세부 결과에서 계산해 중복·누락과 총평/상세 불일치를 방지한다. 잘못된 키, 중복 JSON 키, 근거 없는 전체 대응 및 모순되는 잔여 문구는 계속 거부한다. 세부 미포괄의 잔여 문구가 빠지면 원문 전체를 보존한다.
9. **표 하이라이트**: PDF의 물리적 줄 순서가 아니라 셀별 읽기 순서로 전체 표 행을 대조한다. 떠 있는 표가 제목 위에 표시된 경우에도 같은 페이지의 미사용 행이 유일하게 일치할 때 연결한다. LibreOffice가 표를 후속 문단 아래로 옮기는 경우에는 표 때문에 건너뛴 같은 페이지 구간에서 미사용 원문 전체가 유일하게 일치할 때만 문단을 복구한다. 비슷한 단어만으로 위치를 추정하지 않는다.

## 대표 사례

- `1.2 BOX 매입·INSERT·METAL LATH`: 검색 단계에서는 인방 설치 후보가 남았으나, 전체 원문 검증은 제시 후보에서 대응 근거를 찾지 못했다. 검색 단계의 잔여 오매칭 사례로 후속 평가에 포함한다.
- `2.3(2) 견본 제출·반입 승인`: 내화벽돌 문맥을 사용하며, 블록 전용 후보가 제거됐다. 일반 벽돌의 승인 절차가 후보로 남았지만 전체 포괄 검증은 일부 대응으로 반환했다. 사람의 적용 범위 판단이 필요하다.
- `2.3(3) 내화몰탈 KS L 3202`: 일반적인 KS 적합성 요구와 특정 규격 합격 요구를 구별하여 일부 대응으로 남겼다.
- `2.3(4)-나. 내화벽돌 청소·물축이기 금지`: 직접 대응하는 KCS 본문을 찾아 GPT 전체 대응 결과를 저장했다.
- `2.3(4)-다. 내화몰탈 혼합`: GPT의 전체 대응 판정을 재료 명칭 검사에서 추가 확인 필요로 낮췄다.

## 남은 검증

1. `2.4(2)-가.`, `2.4(2)-다.`, `표 1-3`의 실패 원인을 수정한 후 해당 3건만 다시 검증했다. 모두 HTTP 200, 일부 대응으로 저장됐다. 기존 성공 결과 37건은 재호출하지 않았다.
2. PDF 원문은 9쪽이며 **71개 항목 모두** 좌표에 연결됐다(수정 전 59개). 표가 있는 8·9쪽을 이미지로 렌더링해 실제 행 경계도 확인했다. 이 수치는 위치 연결률이며 의미 매칭 정확도가 아니다.
3. 검색의 `부분 대응`과 전체 검증의 `근거 없음`이 다른 사례가 남아 있다. 정답 후보 및 오매칭 사례를 고정한 뒤 검색 재순위화를 추가 평가해야 한다.
4. 독립적인 담당자 정답 데이터가 없어 **정확도·Recall·삭제 오판율은 아직 측정하지 않았다.** AI 출력이나 자체 유사도 점수를 정답으로 사용하지 않는다. 전체 대응 7개, 재료/수치 차이, 후보 없음, 표 행을 포함해 담당자가 별도로 판정한 뒤 같은 평가 집합으로 비교해야 한다.
5. 로컬 KCS 자료 묶음은 `2026-09-05T18:11:52+09:00`, revision `85ad1d2e4ad9d09af1c392f4a2b8fdf4c01fc5c429251e50e0400e1d2c3e0e75`이다. 공개 서버 revision `e1ccad8f93de8ebd2fb0b59b84ed9f7c61d41ca1beb7118ca68cc0660f56df28`, snapshot `2026-09-09T13:26:34+09:00`과 다르다. 코드 목록 revision은 같지만 raw 묶음 해시는 다르므로 같은 자료로 간주하지 않는다. 배포 후 서버에서 별도 시험본을 재분석하고 실제 서버 결과를 확인한다. 위 수치 차이를 정확도 향상률로 해석하지 않는다.

## 재현 및 증거

`scripts/masonry_pilot.py`는 원본 스냅샷을 덮어쓰지 않으며, `seed`도 이미 존재하는 시험 프로젝트를 덮어쓰지 않는다.

```powershell
# 프로젝트 루트에서 실행. 아래는 추가 API 비용이 없는 조회/캐시 재현 명령이다.
$env:PYTHONIOENCODING='utf-8'
.venv/Scripts/python.exe -m scripts.masonry_pilot report
.venv/Scripts/python.exe -m scripts.masonry_pilot match --cache-only
```

`match`(캐시 전용 옵션 없음)와 `coverage`는 미처리 입력에 유료 OpenAI API를 사용할 수 있다. `coverage-failures.json`에 남은 실패 항목은 자동 재호출하지 않는다. `before.json`, `parsed.json`, `local-match.json`, `after.json`, `source-audit.json`, `preview-audit.json`, `summary.json`이 세부 근거다. 원문 및 API 응답 캐시는 배포/커밋 대상이 아니다.

검증: 1차 전체 백엔드 회귀 테스트 **335개 통과**, 서버 PDF 배치 회귀 사례 1개 추가. 로컬 원문 DOCX 조회 및 격리 API 연결을 확인했다. 테스트 통과율은 매칭 정확도가 아니다. 브라우저 클릭 흐름 전체의 시각 검수는 수행하지 않았다.

배포 전 공개 서버 백업: `989d19ca-c1ac-4900-95e2-e46616994174`, 문서 47개/원문 47개, 복구 가능 검증 완료. API 키·원문·로컬 분석 응답은 Git과 Sites 빌드에 포함하지 않는다.
